## UC-10

* **ID / Code:** UC-10
* **Use Case Name:** Record subscription cancellation
* **Description:** Confirm the effective cancellation date, stop future recurrence and keep existing obligations in collection.
* **Primary Actor:** Administrator
* **Other Initiating Contexts:** External Application can submit intake only; Administrator confirms cancellation.
* **Supporting Actors:** None
* **Scope:** Turbine internal invoicing and collections application.
* **Level:** User Goal
* **Related requirements:** BR-02; UR: UR-02; FR: FR4, FR4.1, FR15, FR4.3, FR15.1, FR15.2; NFR-04, NFR-05, NFR-06.
* **Source:** E pp. 4, 11-12, 14, 17.
* **Stakeholders & Interests:**
  * *Customer:* end the commercial relationship without debt disappearing.
  * *Administrator:* confirm billing consequences.
  * *Assigned staff:* continue prior-debt follow-up.
  * *External Application:* submit controlled intake requests.
* **Preconditions:** The customer/subscription exists. Internal confirmation requires cancellation authority; external intake requires API authentication/scope and cannot itself confirm cancellation.
* **Postconditions:** Confirmation records the effective date and stops applicable future recurring billing. Previous invoices remain collectible; unconfirmed API intake remains pending.
* **Success Guarantee:** Cancellation and old debt are represented separately, following C4 and FR4/FR4.1.
* **Minimal Guarantee:** Intake alone deletes no subscription, erases no debt and creates no paid status.
* **Trigger:** An Administrator records a cancellation or External Application submits intake.
* **Main Success Scenario:**
1. The Administrator supplies the customer, subscription, cancellation reason and effective date.
2. The system validates cancellation authority and customer scope.
3. The system records the request and a task for the responsible user.
4. The system performs [UC-11](UC-11.md) using the authorised internal customer context.
5. The system shows current obligations and billing consequences.
6. The Administrator confirms the effective date.
7. The system stops applicable recurring billing from that date.
8. The system retains previous invoices and collection tasks.
9. The system records the confirmed cancellation outcome.

* **Extensions:**
  * **1a.** External cancellation intake:
    1. External Application submits a controlled cancellation request with its API authority.
    2. The system validates API authentication, scope and limits.
    3. The system records pending intake with a responsible-user task.
    4. The system awaits Administrator confirmation at step 6 after steps 4 and 5.
  * **2a.** Unknown customer identifier:
    1. The system rejects the request without disclosing protected debt data or changing billing.
  * **2b.** Unauthorised customer identifier:
    1. The system rejects the request without disclosing protected debt data or changing billing.
  * **4a.** Current obligations unavailable:
    1. The system retains the request as pending with the [UC-11](UC-11.md) error.
    2. The system requires a successful current query before confirmation.
  * **5a.** Outstanding invoices exist:
    1. The system shows old obligations without blocking cancellation under the current C4 interpretation.
    2. The system retains collection of all prior invoices, including one-off invoices.
  * **6a.** Invalid effective date:
    1. The system records rejection without applying cancellation.
  * **6b.** Confirmation not supplied:
    1. The system retains pending intake without applying cancellation.
  * **7a.** Overlapping billing run:
    1. The system applies the effective date consistently to prevent inappropriate future issuance.
    2. The system retains the C4 next-client-review caveat.
