## UC-20

* **ID / Code:** UC-20
* **Use Case Name:** Send an issued invoice
* **Description:** Request and track invoice delivery or an intentional resend using the existing issued number and preserved PDF.
* **Primary Actor:** Operational User
* **Other Initiating Contexts:** [UC-19](UC-19.md) includes initial delivery. Internal recurring and correction workflows retain their own authorised context; an automatic delivery requires no new staff session.
* **Supporting Actors:** Communication Service
* **Scope:** Turbine internal invoicing and collections application.
* **Level:** User Goal
* **Related requirements:** BR-04, BR-06; UR: UR-04; FR: FR2.4, FR2.7, FR13.1, FR14, FR14.4; NFR-02, NFR-04, NFR-05, NFR-06.
* **Source:** E pp. 3-5, 16.; E pp. 3-5, 8-9, 14.; E pp. 5, 12, 15.
* **Stakeholders & Interests:**
  * *Customer and billing recipients:* receive a correct invoice through an eligible channel.
  * *Assigned staff:* prepare invoices and resolve delivery failures.
  * *Turbine finance staff:* preserve numbering, issued amounts and dispatch evidence.
* **Preconditions:** An issued invoice with its preserved PDF exists. Manual requests require authentication, sending permission and customer scope. Initial automatic delivery uses [UC-19](UC-19.md) authority. Billing contacts, eligible channels and versioned templates are available.
* **Postconditions:** Each attempt records recipients, channel, date, template version and observed result. Sending changes no invoice number, issued amount or original PDF. Queued, sent, delivered when reported, failed and retried remain distinct.
* **Success Guarantee:** An authorised attempt or intentional resend is tracked against the existing invoice with the actual communication outcome.
* **Minimal Guarantee:** A failed sending does not mark the invoice notified. Repeated requests do not duplicate a successful dispatch; an intentional resend is a separate tracked attempt without a new invoice or number.
* **Trigger:** [UC-19](UC-19.md) requests delivery after issuance, or authorised staff request a resend of an issued invoice.
* **Main Success Scenario:**
1. The system receives the existing invoice and sending authority.
2. The system rechecks scope and the preserved PDF availability.
3. The system selects eligible billing recipients.
4. The system prepares the email in the contact language using the applicable template version.
5. The system records the queued attempt with recipients, channel, date and template version.
6. The system requests dispatch through Communication Service.
7. Communication Service reports the observed sending result.
8. The system records only the observed result.
9. The system displays the delivery status independently of issuance.

* **Extensions:**
  * **2a.** Preserved PDF not ready:
    1. The system retains a recoverable delivery request pending the [UC-19](UC-19.md) PDF stage without generating a new invoice.
  * **3a.** No eligible billing contact:
    1. The system records the undelivered outcome without marking the invoice notified.
    2. The system notifies the responsible staff member.
    3. The Operational User may invoke [UC-16](UC-16.md) for delivery follow-up.
  * **4a.** Complementary WhatsApp eligible:
    1. The system prepares a complementary WhatsApp attempt only for stored consent and a valid number.
    2. The system records the separate channel attempt under the same invoice.
  * **5a.** Repeated request for the same attempt:
    1. The system returns the recorded or in-progress outcome without a duplicate dispatch.
  * **7a.** Provider unavailable:
    1. The system records the failed attempt without marking the invoice notified.
    2. The system notifies the responsible staff member.
    3. The Operational User may invoke [UC-16](UC-16.md) for follow-up.
  * **7b.** Bounce reported:
    1. The system records the failed or undelivered state without marking the invoice notified.
    2. The system notifies the responsible staff member.
    3. The Operational User may invoke [UC-16](UC-16.md) for follow-up.
  * **7c.** Only queued or sent status known:
    1. The system retains that observed status without inventing delivered or read evidence.
  * **9a.** Intentional resend after contact correction:
    1. The Operational User requests resend of the existing invoice.
    2. The system rechecks scope and corrected recipients.
    3. The system records a new attempt linked to the same number and original PDF.
    4. The flow continues at step 6.
  * **9b.** Large sending operation:
    1. The system exposes the actual background status and per-item results under FR14.
