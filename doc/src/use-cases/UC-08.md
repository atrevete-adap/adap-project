## UC-08

* **ID / Code:** UC-08
* **Use Case Name:** Run reminders and overdue follow-up
* **Description:** Send eligible invoice reminders using stored terms and current balances, suspending follow-up when authorised.
* **Primary Actor:** None (automatic system behaviour)
* **Supporting Actors:** Communication Service
* **Scope:** Turbine internal invoicing and collections application.
* **Level:** Summary
* **Related requirements:** BR-02, BR-04; UR: UR-05; FR: FR3.2, FR3.3, FR3.4, FR13; NFR-04, NFR-05, NFR-06.
* **Source:** E pp. 5-6, 9, 13, 15.
* **Stakeholders & Interests:**
  * *Assigned staff:* know when invoices become overdue.
  * *Billing contacts:* receive relevant reminders and support details.
  * *Turbine:* follow up debt consistently.
* **Preconditions:** An issued invoice has an outstanding balance and stored terms; templates, channels and schedule are configured.
* **Postconditions:** Dispatch results and next occurrences are stored; overdue changes notify the responsible staff. Settled or validly suspended balances receive no ineligible reminder.
* **Success Guarantee:** Each eligible occurrence produces a tracked attempt without duplicate dispatch.
* **Minimal Guarantee:** Failed delivery is not recorded as success; a reminder never cancels service or silently settles debt.
* **Trigger:** An invoice reminder or overdue occurrence becomes due under the [UC-13](UC-13.md) reminder policy.
* **Main Success Scenario:**
1. The system selects due occurrences using issue dates, due dates and stored customer terms.
2. The system rechecks the outstanding balance.
3. The system checks for an authorised follow-up suspension.
4. The system checks billing recipients and channel consent.
5. The system prepares the applicable day-three, due-date or overdue message with amount, due date and support telephone and email.
6. The system requests dispatch through Communication Service.
7. Communication Service reports the observed dispatch outcome.
8. The system records the observed outcome without inventing delivery or read evidence.
9. The system schedules the next eligible occurrence.
10. The system notifies the responsible staff member of follow-up and overdue changes.

* **Extensions:**
  * **1a.** Weekend or configured holiday:
    1. The system moves only the communication to the next working day under FR3.2.5 and the documented counting/collision policy.
    2. The system retains the legal due date.
  * **1b.** Customer-specific terms:
    1. The system uses the agreed terms instead of the default five days.
    2. The system uses the configured two- or three-day spacing after the actual due date.
  * **2a.** Settled balance:
    1. The system suppresses the reminder occurrence.
  * **3a.** Valid dispute or follow-up pause:
    1. The system suppresses reminders for the suspension period without changing unpaid debt.
    2. The system retains the responsible user review task under [UC-16](UC-16.md).
  * **4a.** No eligible recipient:
    1. The system records an undelivered outcome.
    2. The system notifies the responsible user.
  * **6a.** Occurrence already processed:
    1. The system reuses the recorded occurrence outcome without a second dispatch.
  * **7a.** Provider failure:
    1. The system records a retryable failure without recording success.
    2. The system resumes the failed attempt without repeating a successful occurrence.
  * **6b.** Complementary WhatsApp requested:
    1. The system permits WhatsApp only for a valid number and stored consent.
