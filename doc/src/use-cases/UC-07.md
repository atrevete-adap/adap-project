## UC-07

* **ID / Code:** UC-07
* **Use Case Name:** Reconcile payments with invoices
* **Description:** Match verified provider transactions to invoices and preserve discrepancies or authorised reversals as auditable evidence.
* **Primary Actor:** Operational User
* **Other Initiating Contexts:** Payment Provider notifications supply validated transaction evidence. Scheduled payment queries are internal system behaviour under the authorised integration policy.
* **Supporting Actors:** Payment Provider
* **Scope:** Turbine internal invoicing and collections application.
* **Level:** User Goal
* **Related requirements:** BR-04, BR-05, BR-06; UR: UR-06; FR: FR3, FR3.1, FR14.4; NFR-04, NFR-05, NFR-06.
* **Source:** E p. 6.
* **Stakeholders & Interests:**
  * *Assigned staff:* resolve uncertain matches.
  * *Customer:* have funds allocated correctly.
  * *Turbine finance staff:* explain balances from provider evidence.
* **Preconditions:** The provider connection is configured. Manual actions require reconciliation authority and customer scope; scheduled queries use authorised integration context and inbound notifications are validated.
* **Postconditions:** Verified transactions are allocated once, balances and internal alerts reflect the result, and unmatched/partial/excess amounts remain available for review.
* **Success Guarantee:** A clear match is reconciled or a discrepancy is explicitly retained; paid status requires verified allocations settling the balance.
* **Minimal Guarantee:** Invalid events and provider errors never create payments; original evidence and reversal history remain available.
* **Trigger:** Staff request transaction review, a configured payment-query occurrence becomes due, or Payment Provider supplies a notification.
* **Main Success Scenario:**
1. The system obtains verified successful or settled transaction evidence from Payment Provider.
2. The system records transaction identity, amount, currency, date and reference.
3. The system checks whether the event or transaction has already been processed.
4. The system matches the reference to exactly one eligible open invoice with the same amount and currency.
5. The system allocates the verified transaction once.
6. The system recalculates the invoice balance from the retained evidence.
7. The system records the allocation evidence.
8. The system notifies the responsible staff member of the result.

* **Extensions:**
  * **1a.** Payment query becomes due:
    1. The system queries Payment Provider under the authorised integration context.
    2. The flow continues at step 1 for returned transaction evidence.
  * **1b.** Provider unavailable:
    1. The system records a retryable query failure without marking any invoice paid.
  * **1c.** Invalid notification:
    1. The system rejects the event without creating a payment.
  * **3a.** Duplicate event:
    1. The system returns the prior result without allocating again.
  * **3b.** New event for an already allocated transaction:
    1. The system returns the recorded transaction outcome without allocating again.
  * **4a.** Missing reference:
    1. The system retains the transaction for authorised manual review.
    2. The Operational User may invoke [UC-16](UC-16.md) to track the reconciliation problem.
  * **4b.** Several candidate invoices:
    1. The system retains the ambiguous transaction for manual review without selecting by amount alone.
    2. The Operational User may invoke [UC-16](UC-16.md) to track the reconciliation problem.
  * **4c.** Currency mismatch:
    1. The system retains the mismatch for manual review.
    2. The Operational User may invoke [UC-16](UC-16.md) to track the reconciliation problem.
  * **4d.** Underpayment:
    1. The system records the received amount and outstanding difference as a discrepancy without settling the invoice.
  * **4e.** Overpayment:
    1. The system records the received amount and excess as a discrepancy without discarding funds.
  * **5a.** Manual allocation:
    1. The Operational User selects the allocation with a reason.
    2. The system rechecks reconciliation permission and customer scope.
    3. The system records the allocation with its original evidence.
    4. The flow continues at step 6.
  * **5b.** Reversal requested:
    1. The Operational User supplies the reversal reason.
    2. The system rechecks reversal authority and customer scope.
    3. The system records the reversal without deleting original evidence.
    4. The flow continues at step 6.
