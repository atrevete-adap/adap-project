## UC-02

* **ID / Code:** UC-02
* **Use Case Name:** Maintain customers and import records
* **Description:** Maintain customer companies and contacts, including validated CSV onboarding through an administrator-only alternative.
* **Primary Actor:** Operational User
* **Supporting Actors:** None
* **Scope:** Turbine internal invoicing and collections application.
* **Level:** User Goal
* **Related requirements:** BR-01, BR-06; UR: UR-01, UR-10; FR: FR1, FR1.1, FR1.2, FR1.3, FR1.6, FR1.4, FR1.7, FR1.8; NFR-01, NFR-02, NFR-03, NFR-04, NFR-05.
* **Source:** E pp. 2, 4, 7-8, 12, 14-15.; E p. 7.
* **Stakeholders & Interests:**
  * *Assigned staff:* keep their customer portfolio accurate.
  * *Billing contacts:* receive correct documents at the intended address.
  * *Administrator:* import customers without duplicates or silent overwrites.
* **Preconditions:** The actor is authenticated with customer-management permission and current customer scope. CSV import additionally requires Administrator authority and import permission.
* **Postconditions:** Confirmed changes and their actor/time are stored; CSV results identify each committed/rejected row. Deactivation retains issued documents and debt.
* **Success Guarantee:** The authorised customer/contact operation is saved and available in the customer timeline.
* **Minimal Guarantee:** Rejected or stale operations leave committed data intact; no automatic merge or historical invoice rewrite occurs.
* **Trigger:** The user creates or opens a customer, or an authorised Administrator selects CSV import.
* **Main Success Scenario:**
1. The Operational User searches for a customer by company, contact, tax identifier or email.
2. The system displays matches within the current customer scope.
3. The Operational User selects a customer record.
4. The Operational User enters the company, tax, currency, status and contact data, including billing recipients, language and WhatsApp consent.
5. The system validates the required data and country-specific formats where known.
6. The system checks for duplicate identifiers.
7. The system checks for a conflicting change.
8. The system previews the billing consequences of the change.
9. The Operational User confirms the change.
10. The system saves the permitted change with its actor and time.
11. The system displays the customer timeline and documents.

* **Extensions:**
  * **1a.** New customer:
    1. The Operational User starts a new company record.
    2. The system offers the customer defaults described in the shared rules.
    3. The flow continues at step 4.
  * **3a.** Administrator CSV import:
    1. The Administrator uploads the CSV file.
    2. The Administrator maps its columns.
    3. The system previews each row and its errors.
    4. The Administrator confirms import of valid rows.
    5. The system applies authorised rows without silent overwrites.
    6. The system reports created, updated, rejected and unprocessed rows with reasons.
  * **3b.** CSV errors require correction:
    1. The Administrator corrects the file before confirming import.
    2. The system repeats the preview and duplicate checks.
  * **5a.** Missing required data:
    1. The system identifies the missing fields without discarding valid input.
    2. The system distinguishes issuance requirements from recommended customer data.
  * **6a.** Possible duplicate:
    1. The system warns about the matching historical record without merging companies.
    2. The Operational User explicitly selects reactivation when appropriate.
    3. The system preserves that record and its history.
  * **7a.** Concurrent change:
    1. The system rejects the stale write without overwriting committed data.
  * **9a.** Customer scope lost:
    1. The system rejects the unauthorised write without changing committed data.
  * **8a.** Status change:
    1. The system previews the consequences for billing.
    2. The flow continues at step 9.
  * **8b.** Logical deletion:
    1. The system previews deactivation without deleting history, issued documents or old debt.
    2. The flow continues at step 9.
  * **8c.** Only billing contact would be removed or deactivated:
    1. The system warns before confirmation.
    2. The flow continues at step 9.
  * **8d.** Inactive recipient selected:
    1. The system warns about the inactive contact before confirmation.
  * **11a.** Document download:
    1. The Operational User requests a document.
    2. The system rechecks access to that document.
    3. The system provides the permitted document.
  * **11b.** Bulk export or update:
    1. The Operational User selects records and an operation.
    2. The system previews the affected count and sensitive effects.
    3. The Operational User confirms the operation.
    4. The system rechecks each item against current scope.
    5. The system reports each item outcome.
    6. The system audits sensitive exports.
